# ADR-002: O/R マッパーに MyBatis を採用する

## ステータス
採用（Accepted） - 2026-01

## コンテキスト
本プロジェクトでは、PostgreSQL データベースに対する CRUD 操作と、動的検索（部分一致・ソート・フィルター）が必要である。O/R マッパーの選定にあたり、以下の観点で比較検討した。

- SQL の制御のしやすさ
- 動的クエリの構築のしやすさ
- 学習コストと日本での普及度

## 検討した選択肢

### 1. MyBatis
- ✅ SQL を XML で明示的に管理でき、複雑なクエリにも対応しやすい
- ✅ 動的 SQL（`<if>`, `<choose>`, `<foreach>`）による柔軟な検索条件の構築
- ✅ 日本のエンタープライズ開発で広く採用されている
- ⚠️ SQL を直接書く必要があるため、生産性は JPA に劣る場合がある

### 2. Spring Data JPA (Hibernate)
- ✅ エンティティ定義から自動で SQL を生成（開発速度が高い）
- ✅ Spring Boot との統合が最もシームレス
- ⚠️ 複雑な結合クエリや動的検索の実装が煩雑になりやすい
- ⚠️ N+1 問題などのパフォーマンス課題に対する知識が必要

### 3. jOOQ
- ✅ タイプセーフな SQL ビルダー（コンパイル時にエラーを検出）
- ✅ 複雑なクエリでも Java コード内で安全に記述可能
- ⚠️ 商用ライセンスが必要なケースがある
- ⚠️ 日本での採用事例が少ない

## 決定
**MyBatis** を採用する。

本プロジェクトでは一覧画面の動的検索（カラムごとの部分一致・ソート切り替え）が主要機能であり、XML による動的 SQL の柔軟性が最も重要であると判断した。また、SQL を明示的に管理することで、パフォーマンスチューニングやデバッグが容易になる点も考慮した。

## 結果
- 動的検索・ソート機能を MyBatis の `<if>` タグで簡潔に実装できた
- SQL の可読性が高く、レビューやデバッグが容易だった
- 多対多の関連（todo_assignments）も `<collection>` タグで適切にマッピングできた
