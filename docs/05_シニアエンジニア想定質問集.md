# シニアエンジニア想定質問集

## Q1. なぜメンバー操作を画面制御ではなく `@PreAuthorize` で守ったのですか？

画面のボタン非表示は UX の制御であり、セキュリティ境界ではないためです。HTTP リクエストは curl や Postman から直接送れるので、重要な認可はサーバー側で必ず検証します。今回はメンバー登録・更新・削除を ADMIN のみに限定しました。

## Q2. TODO の編集権限とメンバー管理権限を分けた理由は？

責務が違うためです。TODO_ADMIN は TODO 運用の管理者ですが、ユーザー作成や権限変更まで許すと権限昇格のリスクがあります。メンバー管理は ADMIN に寄せ、TODO 管理は TODO_ADMIN と ADMIN に許可する設計にしました。

## Q3. パスワードはハッシュ化されているのに、なぜ API から除外するのですか？

ハッシュであっても認証情報なので、レスポンスに含める必要がありません。漏えいした場合、オフライン解析や他サービスへの攻撃材料になります。DTO から削除し、アプリの外へ出ない形にしました。

## Q4. XSS 対策で `innerHTML` をやめた理由は？

`innerHTML` は文字列を HTML として解釈します。DB に保存された文字列が `<img onerror=...>` のような内容だと、一覧再描画時に実行される可能性があります。`textContent` を使うと HTML ではなく文字として描画されるため安全です。

## Q5. username / email の UNIQUE 制約を partial unique index にした理由は？

このアプリは論理削除を使っているためです。通常の UNIQUE 制約だと、削除済みユーザーの username / email も永久に使えません。`WHERE deleted_flg = FALSE` の partial unique index にすることで、有効ユーザーだけ重複を禁止できます。

## Q6. 重複チェックを DB だけでなくアプリ側にも入れた理由は？

DB 制約だけでも最終防衛線としては有効です。ただし制約違反をそのまま出すとユーザーには分かりづらい 500 エラーになりがちです。アプリ側でも事前にチェックし、フォームの入力エラーとして返せるようにしました。

## Q7. ステータスを enum にした理由は？

DB 保存値と画面表示を分け、取り得る値をコード上で明確にするためです。`TODO`, `IN_PROGRESS`, `DONE` のような安定した値を DB に保存し、画面では `未着手`, `進行中`, `完了` と表示しています。

## Q8. 完了日時 `completed_at` はどのタイミングで設定されますか？

TODO のステータスが `DONE` に変わったタイミングで設定します。すでに `DONE` の TODO を編集しただけなら元の完了日時を維持します。`DONE` から別ステータスに戻した場合は、未完了扱いにするため `completed_at` をクリアします。

## Q9. 変更履歴はどのように記録していますか？

更新前の TODO を取得し、更新後に再取得して項目ごとに比較しています。値が変わった項目だけ `todo_histories` に保存します。担当者は名前の一覧をソートして比較し、順序差分だけで履歴が増えないようにしています。

## Q10. コメントと変更履歴を同じテーブルにしなかった理由は？

用途が違うためです。コメントはユーザーが入力する会話データで、変更履歴はシステムが記録する監査データです。検索や表示、保持ルールが将来分かれる可能性があるため、テーブルを分けています。

## Q11. ダッシュボード集計を Java ではなく SQL で行った理由は？

件数集計やグルーピングは DB が得意だからです。全 TODO を Java に読み込んで集計すると、データ量が増えたときにメモリや通信量が無駄になります。SQL で集計して必要な結果だけ返す設計にしました。

## Q12. 今回のテストで最も重視したことは？

レビューで High 指摘だった認可と情報漏えいです。特に「非 ADMIN が直接 POST してもメンバー操作できないこと」と「API に password が出ないこと」は、再発すると危険なので MockMvc テストで固定しました。

## Q13. まだ改善できる点はありますか？

あります。次に取り組むなら、CSRF エラーや認可エラーの専用画面、コメント削除、履歴検索、ページネーション、Testcontainers による PostgreSQL 統合テスト、CI の追加が候補です。

## Q14. この実装で実務らしい点はどこですか？

単に機能を増やしただけでなく、認可、情報漏えい、XSS、DB 制約、監査履歴、Docker 起動、テストをまとめて整えた点です。業務アプリでは「便利に動くこと」と同じくらい「壊れにくく安全に運用できること」が重要です。
